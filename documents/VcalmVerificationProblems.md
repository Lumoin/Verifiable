# VCALM verification problems

The verification endpoints report HTTP 200 when the verification process completes, including when its result is `verified:false` ([VCALM §3.3.2](https://www.w3.org/TR/vcalm-1.0/#verify-presentation): "A 200 status indicates the verification process itself succeeded, regardless of whether the presentation and/or credentials were determined to be valid or invalid."). Request-shape failures report HTTP 400 and the payload cap reports HTTP 413. Errors set `verified:false`; status and validity-period problems are warnings ([VCALM §3.8.1](https://www.w3.org/TR/vcalm-1.0/#verification-errors-vs-warnings): "Errors are ProblemDetails relating to cryptography, data model, and malformed context and are unrecoverable. Warnings are ProblemDetails relating to status and validity periods and might be recoverable or leave the subsequent action to the discretion of the application."). A declared schema that is never checked, because its fetch ended on its own budget or the request's dependency budget was already exhausted, is a data-model error, so it never leaves `verified` true. A status that could not be established, whether its fetch failed, ended on its own budget or was never attempted, is a warning, as VCALM classifies every status problem, so it does not by itself make `verified` false.

The VCALM Working Draft of 21 August 2026 changes nothing normative in sections 2.4, 3.3.1, 3.3.2, 3.8 and 3.8.1 relative to the May draft.

Library-defined types share one base, `VcalmProblemTypes.LibraryProblemTypeBase` (`https://verifiable.lumoin.com/problems#`). They are problem types under the definer's control ([RFC 9457 §4](https://www.rfc-editor.org/rfc/rfc9457#section-4)), not specification-defined error codes. Every title is the type's code. Details identify the cause without copying exception messages, resolver diagnostics or policy decisions, and include only identifiers the caller supplied ([VCALM §3.8](https://www.w3.org/TR/vcalm-1.0/#error-handling): "Implementers are strongly advised to sanitize all server errors in production environments").

All VCDM codes use `https://www.w3.org/TR/vc-data-model#`, the base [VCDM 2.0 §7.2](https://www.w3.org/TR/vc-data-model-2.0/#problem-details) defines, including `CRYPTOGRAPHIC_SECURITY_ERROR`, `MALFORMED_VALUE_ERROR`, `RANGE_ERROR` and `PARSING_ERROR`. Bitstring Status List codes use `https://www.w3.org/ns/credentials/status-list#`. VCALM's own option error uses `https://www.w3.org/TR/vcalm#UNKNOWN_OPTION_PROVIDED`.

The explicit `presentation` request alternative is an unproofed presentation whose contained credentials are verified. Missing securing on the `verifiablePresentation` alternative is a parsing error.

URL syntax is checked before resolution. A syntactically valid non-DID URL that the configured DID resolver cannot retrieve reports `INVALID_CONTROLLED_IDENTIFIER_DOCUMENT`. `InvalidDidDocument` is the primary DID Resolution error. Its optional `DidResolutionResult.InvalidDocumentReason` states why the resolver refused the document: `IdMismatch` reports `INVALID_CONTROLLED_IDENTIFIER_DOCUMENT_ID`; `Malformed`, `MissingRequiredProperty`, `EmbeddedIdentifierOutsideDid` and an absent reason report `INVALID_CONTROLLED_IDENTIFIER_DOCUMENT`. `DidResolver` states `IdMismatch` when a method returns a document for another DID without an equivalence guarantee, and the did:web resolver states a reason at each of its refusals. This keeps the distinction between [CID §3.3 steps 5 and 6](https://www.w3.org/TR/cid-1.0/#retrieve-verification-method) when the resolver refuses the document before returning it. The did:web resolver judges a fetched document's conformance against the document's own `id` first, so embedded verification method identifiers or controllers outside that `id` are `EmbeddedIdentifierOutsideDid` (step 5), and only then compares that `id` with the requested DID (`IdMismatch`, step 6): a consistent document for another subject is an identifier mismatch. It fetches `did.json` under the one 8 MiB response bound, `OutboundFetchPolicy.DefaultMaxResponseBytes`, that the did:webvh and did:webplus resolvers also read, asks the transport to enforce it, and never parses a larger body; such a fetch reports `NotFound`. A returned document whose own ID differs from the requested controller URL also reports the ID error. Invalid document-level controller entries make the document nonconforming; method-level type, ID, controller or key failures report `INVALID_VERIFICATION_METHOD`. A JWK without a string `kty` member, which [RFC 7517 §4.1](https://www.rfc-editor.org/rfc/rfc7517#section-4.1) requires, is an input result decided before key conversion.

Transformation classification depends on the phase alone. Context-fetch failures (including `HttpRequestException`), malformed JSON-LD and canonicalization faults all report `PROOF_TRANSFORMATION_ERROR`. At the credential and presentation proof boundaries, an `OperationCanceledException` raised while the caller's token is still live takes the active phase's code: `PROOF_TRANSFORMATION_ERROR` during transformation, otherwise `PROOF_VERIFICATION_ERROR`. Every verification boundary — Core's canonicalization, and VCALM's proof, controller-resolution, status and schema boundaries — recognises a cancellation that a dependency reports inside an exception of its own, whether as an inner exception or as any one of an aggregate's inner exceptions, as that cancellation: Core's Data Integrity verification rethrows the `OperationCanceledException` it finds rather than reporting a context validation failure, and the VCALM boundaries treat it as the dependency's own budget while the caller's token is live. At the controller-resolution boundary an own-budget cancellation means the controller document could not be retrieved, so it reports `INVALID_CONTROLLED_IDENTIFIER_DOCUMENT`, as a transport failure there does ([CID §3.3](https://www.w3.org/TR/cid-1.0/#retrieve-verification-method)). The detail says the fetch or operation was cancelled by its own budget. The caller's own cancellation propagates, bare or carried, so an abandoned request produces no verification result, and these boundaries never catch `OutOfMemoryException`. A context validation failure after transformation reports the library context error. An unclassified failure outside transformation reports `PROOF_VERIFICATION_ERROR` with the phase and no dependency diagnostics. Selective-disclosure structural rejection reports `PROOF_VERIFICATION_ERROR`; an actual false signature verdict reports the cryptographic-security error.

Once a dependency fetch of one verify request — a JSON-LD context, a controller document, a status list, or a schema document — ends on its own budget while the caller's token is still live, no further dependency fetch is attempted for that same request: the remaining contained credentials and steps report the problem type their own phase reports for a failed fetch of that kind, with a detail ending "an earlier dependency of this request exhausted its budget." A controller document or a transformation reports its error, a declared schema `MALFORMED_VALUE_ERROR`, an error that never leaves `verified` true, and a status entry `STATUS_RETRIEVAL_ERROR`, a warning. This bounds the cost one stalling host can impose on a request to one fetch, whatever number of credentials or steps the request carries. Within one request the DID resolver is also asked only once per controller document URL: every proof and contained credential that names the same controller shares that one answer, a document or a failure, which lives on the request's own context and never reaches another request or tenant. The number of proofs a credential or presentation may carry is bounded by `VcalmCredentialVerification.MaxProofsPerDocument`, and the proofs of one document that name the same verification method share one check of that method, so its relationship lookup and key decode run once.

A status-list fetch that ends on its own budget while the caller's token is still live is the status phase's own failure and reports the `STATUS_RETRIEVAL_ERROR` warning, the type a failed retrieval already produces. A schema-document fetch that ends the same way leaves that declared schema unchecked, which is the `MALFORMED_VALUE_ERROR` error above, its detail naming the stall; a schema document the resolver simply does not return leaves the entry Indeterminate — `verified:false` with no asserted `ProblemDetail` — as [VC JSON Schema §4.2](https://www.w3.org/TR/vc-json-schema/#evaluation) evaluates a schema it could not resolve. The entries after either stall are not attempted and report the problems above.

Every path that signs over an input proof refuses one that is missing `type`, `verificationMethod` or `proofPurpose` with a `MALFORMED_VALUE_ERROR` 400 before any signing, per [VCALM §2.4](https://www.w3.org/TR/vcalm-1.0/#options): "Implementations MUST throw an error if an endpoint receives data, options, or option values that it does not understand or know how to process." Credential issuance refuses such an existing proof in both the Proof-Set and the Proof-Chain configurations, so `/credentials/issue` and the exchange workflow's issuing step meet the same refusal; `/credentials/derive` and `/presentations` refuse a base proof or a contained credential's proof likewise, and the holder service behind them refuses the same input itself, whoever calls it. An exchange workflow's credential template that renders a `proof` member hands the issuing step an existing proof, handled under the instance's existing-proof configuration exactly as a caller's own: the credential model the rendered JSON deserializes into decides whether it carries one, so a member name spelled with JSON escapes is the same `proof` member; the default configuration refuses it with the [VCALM §3.2.1](https://www.w3.org/TR/vcalm-1.0/#issue-credential) existing-proof error, and no configuration chains onto an incomplete one. No signing path re-serializes or chains onto a defective input proof.

Missing proof options reach the verification layer: the JSON proof converter preserves them, and VCALM checks every credential proof and presentation proof for `type`, `verificationMethod` and `proofPurpose` before invoking Core, as [Data Integrity §4.4](https://www.w3.org/TR/vc-data-integrity/#verify-proof) requires. The converter keeps a proof's `verificationMethod` whatever its `proofPurpose`, including a purpose it does not model and a missing one, so the proof reaches the verifier's option checks, which report `PROOF_VERIFICATION_ERROR` for the missing or unexpected purpose; reading then writing a proof with an extension purpose keeps both members, and two references to one verification method under different purposes are different references. Core's Data Integrity verification also refuses a missing `type` in credential verification, interactive and linked presentation verification, and BBS and ECDSA-SD base and derived verification, including their raw-key entry points, reporting `MissingVerificationMethod` for the combined mandatory-proof-option condition; the BBS and ECDSA-SD raw-key entry points refuse a proof whose purpose is not `assertionMethod` exactly as the resolving ones do, so a proof with an unmodelled purpose verifies nowhere.

An uninitialized crypto registry, or one that returns no verification function, reports `UNSUPPORTED_SECURING_MECHANISM`. A registry matcher that throws, including one that throws for an absent algorithm, reports `PROOF_VERIFICATION_ERROR` without its diagnostics.

Schema failures include only the caller's schema identifier in their detail, never the validator's message or instance/keyword paths.
